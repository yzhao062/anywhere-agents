# Implement-Review

On `/vet` or `$implement-review`, run the review loop for the requested target. A subagent of the coordinator, or the coordinator's own checks, cannot fill a reviewer slot. An Auto-terminal round reports the reviewer, its review file, and the Phase 2 health-check result, or says that intake is pending or failed.

## Overview

The coordinator sends the changes to one or more reviewers, categorizes the feedback, revises, and iterates. Codex is the default reviewer, through terminal relay (manual copy-paste, default on every platform) or Auto-terminal (opt-in subprocess dispatch), which also drives the Agy, Claude, and Grok backends. A reviewer driven by hand only needs the `Review-<AgentName>.md` save contract in Phase 1c. Reviewer defaults and coordinator rewrites follow Path selection.

## Round checklist

Two standing rules come first, then the steps of a round in order. Each step states its decision once and links the section with its procedure.

A. **Claude slot when Codex coordinates.** This rule covers the Claude slot only when Codex coordinates; other pairs keep their usual dispatch, waiting, and failover, and its verdict list serves every `await-review.py` call (steps 6 and 8). Start `dispatch-claude` on a resumable exec tool and keep its handle and `STATE-DIR`. Claude's text can stay empty until its final response, so an empty tail, `ALIVE`, or a pre-publication `STALL` leaves the review pending, even after 15 minutes. Before the first wait, run `<python> <scripts-dir>/await-review.py --state-dir <abs-path> --round <N> --review-file Review-Claude-Code.md --timeout 0` to establish the original deadline. The script has no shell wrapper, `--review-file` defaults to `Review-Codex.md`, `<python>` comes from `<state-dir>/python-interpreter` when the dispatcher wrote one (`dispatch-claude` writes none; then resolve one as section 1c says), and `<scripts-dir>` follows the lookup order of the other scripts. A custom `--round-budget` goes on that first call, before the deadline is stamped, and a new deadline is never stamped. Wait on the retained handle with empty-input `write_stdin` (a confirmed native completion notification also serves), requesting `yield_time_ms=180000` when supported, capped by the remaining round budget and any smaller host limit, as a maximum window and not a fixed delay. After each completed wait, and before marking the slot complete, read the dispatcher exit status first: nonzero is a confirmed failure that wins over `ALIVE` and goes through [1c. Send to reviewer](#1c-send-to-reviewer), and exit 0 still needs the report and step 7. While the dispatcher is pending, make one `--timeout 0` check for publication or the deadline, then continue the same handle unless a documented checkpoint is reached. Resume an outer execution cell that yields early and never terminate it. If the handle is lost ([references/claude-backend.md](references/claude-backend.md)), run the step 6 command with the original deadline, and never wait only on a long-running resolver, which cannot see a dispatcher exit without publication. A tool yield or an expired wait is not failure. Do not conclude the review, drop the slot, or cancel the dispatcher or reviewer to end the turn (`terminate: true`, Ctrl-C, or `kill`): cancellation by the coordinator is not a backend failure and does not allow Single-source completion. Add no fixed sleep, log rereads, or repeated progress messages. Keep the original 60-minute deadline unless the user names another budget, arm no shorter harness kill timer, and keep the deadline across yields and scheduled wakeups. A user-requested stop pauses monitoring and does not make silence a failure. Publication alone is not proof the worker exited, and sequential mode waits on that proof ([Path selection](#path-selection)). A published report alone is not a conclusion: run step 7, reading a saved `stall-warning` as the Check 9 inspection, because a pre-publication silence warning is no permission to abandon the reviewer. Verdicts: `DONE` or `REVIEW-READY` means read the report and run step 7 (a `REVIEW-READY` review can still fail Checks 4 to 10); `ALIVE` means the round is unproven, so check again until a verdict or the deadline; `STALL`, `TIMEOUT`, and `REAP-UNKNOWN` stay checkpoints: `STALL` surfaces the silence warning and leaves the review pending (step 6), and `TIMEOUT` and `REAP-UNKNOWN` report the specific incomplete state and pause monitoring, never killing the reviewer or inventing a deadline; of these verdicts only `DEAD` and `STREAM-DEAD` confirm a failure, and they go through section 1c ([references/failover-and-recovery.md](references/failover-and-recovery.md)). Stop monitoring the slot once its result reaches intake.

B. **When the loop stops.** Stop when the user says the review is done or approved, when the user decides to stop iterating, or when no new or still-open finding meets the Will fix bar. A reviewer that still blocks on a `Deferred` item does not hold the loop open; name those items in the summary. Then present a short summary: total rounds, key changes made, and unresolved points from the last review. Procedure: [Phase 4: Conclude](#phase-4-conclude).

1. **Prerequisites.** Follow [Prerequisites](#prerequisites): the usage snapshot, staged changes and drift, and the `Review-*.md` exclusion. When the user asks for a plan review or a plan-first signal holds, start at [When to plan-review first](#when-to-plan-review-first) and read [references/plan-review.md](references/plan-review.md); only the staged-change and drift checks wait until the plan passes.

2. **Pre-review checks.** Run the content-type checks in [Pre-Review Checks (optional)](#pre-review-checks-optional) before building the request.

3. **Channel and reviewers.** Choose both by [Path selection](#path-selection). Reasoning effort is a one-way ratchet: the registry's effort is the floor, not a target. The dispatching agent may raise one round above it with a higher `CODEX_DISPATCH_REASONING` when the change is hard enough to earn deeper reasoning (mirrored copies of one file, caching or state lifetime, or a risk of failing silently rather than loudly), and must never pass a lower one, so the worst case is a round not deepened, never one weakened. A higher tier lengthens wall-clock, so raise the dispatch timeout in the same step or the round is killed before it writes anything. When the budget buys one deeper round or two at the floor, prefer another round while the artifact is still changing (their relative yield is unmeasured, so treat this as a default), and raise the tier for the closing round or when the change is subtle enough that a first read is unlikely to reach it. See [references/codex-backend.md](references/codex-backend.md) before raising the tier or timeout.

4. **Build the request.** Assemble it from [1b. Build the review context](#1b-build-the-review-context), choosing the lens with [references/review-lenses.md](references/review-lenses.md). A snapshot backend such as Agy reviews the exported index, so a gitignored `PLAN-*.md`, an untracked evidence note, or an untracked local override never reaches it, and its review would be silently ungrounded. Paste each such input into the request once under a `--- SUPPLIED INPUT: <path> ---` heading (plan-review step 3). The relay tells the reviewer to read those copies and never the original worktree, and supplied policy stays distinct from repository material, which the relay treats as untrusted.

5. **Dispatch.** Send the request by [1c. Send to reviewer](#1c-send-to-reviewer), which sets up the failure definition and the failover queue at round start. Dispatchers take `--expected-review-file Review-<Reviewer>.md`, and `health-check` and `await-review.py` take `--review-file Review-<Reviewer>.md`, where `<Reviewer>` is the backend's own name: `Codex`, `Claude-Code`, `Antigravity`, or `Grok`.

6. **Watch.** Run one watcher per reviewer under [1d. Auto-watch (Terminal-relay and Auto-terminal channels)](#1d-auto-watch-terminal-relay-and-auto-terminal-channels). A `STALL` exit 3 is not a death: surface the silence warning and inspect or keep monitoring, and do not terminate the dispatch or set sticky downgrade from silence alone. Silence is never terminal: `DEAD` needs `stream-death` paired with a completed `stream-reap-complete`, and neither a quiet tail nor a review published under the wrong round marker is that evidence, so no shorter idle window may be promoted to a death certificate. If a reviewer dies without writing a marker, `await-review.py` keeps returning `ALIVE` and the round's own timeout ends it. A harness notice that the dispatch or watcher was stopped (`killed` in a background-task notification) concerns the harness's task wrapper, not the reviewer, which runs detached: do not conclude failure, redispatch, or set sticky downgrade from it, and a lost watcher is no corroboration. Resolve it in the foreground, since a background probe would be exposed to the same stop, with `<python> <scripts-dir>/await-review.py --state-dir <abs-path> --round <N> --review-file Review-<Reviewer>.md` (interpreter and `<scripts-dir>` as in rule A). It replaces the watcher for the rest of the round, and rule A gives its verdicts. A watcher `REAP-UNKNOWN` is resolved with the same command, and only the resolver's own checkpoint verdicts pause monitoring.

7. **Health check.** For Auto-terminal, run `health-check --state-dir <abs-path> --round <N> --review-file Review-<Reviewer>.md` with the `STATE-DIR` the dispatcher printed. Read its stdout, never only the exit code: a `WARN` exits 0, and it exits non-zero only for a `FAIL` of Checks 1 to 6 or 10 or missing or stale `<state-dir>/pre-mtime` or `<state-dir>/timestamp`. Any `FAIL` refuses that review and routes it through section 1c while the other slots stay active. A `WARN` from Check 7, 8, or 9 or a Substance heuristic is inspected and is not by itself a refusal: read what the check flags, record the reading in the round summary, and advance. Read for `check-7` the `lines=` it names in `Review-<Agent>.md`; for `check-8` the matching failure lines in `<state-dir>/tail` and, when present, `<state-dir>/tail.stderr-tmp` (where the Claude and Agy dispatchers write stderr), and when `breakdown=` includes `recovered:` also `<state-dir>/backend-failure` and whether the review ends cleanly, accepting that review's verdict only after checking it for placeholders, narration, and truncated findings; for `check-9` `<state-dir>/stall-warning` and whether the review ended cleanly; for `substance-1` the `elapsed=` and `prompt=` pair; for `substance-2` the file:line anchors (`0-anchors`); for `substance-3` the scope-challenge axes in `missing-axes=`. Ask the user only when an inspection finds a defect: a tool failure that blocked verification, a truncated or placeholder review, a missing verification, or `WARN check-8 1 missing-dispatch-tail`, which leaves dispatch health unconfirmed and is never read as Check 8 hit 0. When the review file is missing, Check 1 hard-fails while Checks 8 and 9 still run on the tail and stall warning. Every saved review needs one standalone `Verification status: VERIFIED` or `UNVERIFIED` line: `VERIFIED` only after at least one relevant verification command completed, with the exact commands and outcomes in Verification notes, and a run with none says `UNVERIFIED` with `Commit verdict: UNVERIFIED` and cannot issue `PASS` or `BLOCK`. Check 10 rejects an `UNVERIFIED` status or verdict, a `PASS` or `BLOCK` without `VERIFIED`, conflicting markers, and `VERIFIED` beside notes that report no execution, so a `BLOCK` with `VERIFIED` and concrete outcomes passes, and `FAIL check-10` is a hard intake failure. Only after a fresh review says Codex could not run `git diff` (dispatch exit 0, fresh `Review-Codex.md`), retry Auto-terminal once with an embedded-diff prompt before the failure is routed through section 1c; with the default `--sandbox danger-full-access` this should never fire. Its findings are diff-scoped and prone to false positives on claims that depend on non-diff code, so a Medium finding from it needs step 10 before it is applied, and a retry that fails or records only blocked verification is a confirmed failure routed through section 1c. Procedure: [Phase 2.0: Health check (Auto-terminal only)](#phase-20-health-check-auto-terminal-only); see [references/health-check.md](references/health-check.md) when its read condition holds.

8. **Intake.** For Terminal-relay, auto-watch `DONE` is enough to start intake. For Auto-terminal it is necessary but not sufficient: advance a reviewer with no inspection only when all eight hold: `DONE <path>` or a resolver `REVIEW-READY <path>` for a file with the current round marker; the dispatch subprocess exited 0, or the harness reported the task stopped and `await-review.py` then returned `REVIEW-READY`; Checks 1 to 6 pass; Check 10 passes; Check 7 hits 0 phrases; Check 8 hits 0 markers; Check 9 finds no `stall-warning` file; the Substance heuristics flag 0 signals. If the exit evidence, Checks 1 to 6, or Check 10 fails, refuse that review and route its dispatch through section 1c while the other slots continue. A hit on Check 7, 8, or 9 or a Substance heuristic is inspected under step 7 and is not by itself a refusal. `TIMEOUT` and `REAP-UNKNOWN` also stop at a human checkpoint; a `STALL` leaves the review pending under step 6 and never starts intake by itself. Consolidate only after every expected reviewer has a ready report or a confirmed failure (or the user says the reviewers are done), and keep a slot pending while its dispatch is active. Read only `Review-*.md` files that are current-round (first line `<!-- Round N -->`) and from an expected reviewer, and report every ignored file by filename and reason (stale-round, empty, unreadable, unexpected) before presenting findings. Flag a current-round unexpected file to the user before including or excluding it: mtime against the Phase 1c emission time is a noisy secondary signal only, a corroborating signal is required before including it, and it is never included or excluded silently. When the expected set is unknown, use mtime only to rank candidates and ask the user which current-round files belong to this review. For an expected reviewer whose file is missing, stale, or empty with no confirmed dispatch failure, send a follow-up prompt naming that reviewer, then ask the user to paste its feedback directly if the file is still missing, empty, or stale. Procedure: [Phase 1d coordination (Auto-terminal-specific silent-intake rule)](#phase-1d-coordination-auto-terminal-specific-silent-intake-rule); the partition is in Phase 2.1.

9. **Classify and act.** With two or more current-round sources, classify each new finding as Convergent (two or more reviewers raise substantially the same point), Convergent with differences (same problem, different severity, scope, or remedy: keep each reviewer's severity and fix, and use the highest severity until the user or implementer resolves it), Single-source (label the source), or Divergent (opposite positions: flag it, show both positions, and classify it like any other finding). If only one current-round source remains after step 8 although more were expected, label every finding Single-source; a single-reviewer round's one source is complete intake. Acknowledge each point, and check the reviewer's New and Previously raised split, making it yourself from the round history when the reviewer did not. Mark a new finding Will fix (clear, actionable, correct, and worth a revision), Decline (correct but not worth a revision, and never a risk to user data), Needs discussion (ambiguous or potentially wrong), or Disagree (explain why). Mark a previously raised finding Fixed (no action), Still open (the fix did not land or was incomplete: treat as Will fix unless the user overrides), Reopened (flag it to the user: it needs a decision and is never re-argued silently), or Deferred (no action unless the user reconsiders). Fold in the outcomes of step 10 and record the categorized list in the round summary. Do not ask before applying Will fix and Still open items (step 11 applies them after step 10), and record each Decline as Deferred with a one-line reason, also without asking. Ask the user only about Needs discussion, Disagree, and Reopened items, and act on them only after the answer, so a Divergent finding asks only when it lands in Needs discussion or Disagree. If no new or still-open finding meets the Will fix bar, skip step 11 and apply rule B. Procedure: [Phase 2.1: Partition and classify (all channels)](#phase-21-partition-and-classify-all-channels).

10. **Verify claims.** After classifying and before applying, verify a finding that makes an objectively checkable factual claim (a citation, code behavior, a link, a count, a compile error) when it is High priority, or Medium and from the embedded-diff retry channel, or the user asks for verification of a Medium or Low one. Skip it when the reviewer's Verification notes already cover that claim with a method that resolves it (trust that check unless contradicting evidence appears), when the fix is trivially correct or the cheapest verification takes longer than the user can wait, and for stylistic, opinion-based, or structural findings. Verified means the Will fix bar decides. Refuted means do not apply the fix whatever its category: push back through a follow-up reviewer prompt that cites the evidence (command run, output, URL fetched, file inspected), which the user may override by asking to apply anyway. Inconclusive means surface the ambiguity and let the user decide. Add each Refuted or Inconclusive finding, with its evidence or reason, to the next round's `Prior findings` block. Procedure: [Phase 2.5: Verify Factual Claims (when triggered)](#phase-25-verify-factual-claims-when-triggered); methods are in [references/health-check.md](references/health-check.md).

11. **Revise.** Apply Will fix items and the Needs discussion points the user approved in place: rewrite, move, or cut the named passage, and add material only for an identified gap. For a paper, proposal, or plan, record its size each round in the same unit, and after two consecutive rounds of growth with no new result or step, consolidate before the next dispatch. Cut unneeded defenses and move process history that supports no retained claim to the records. Update the round history (Resolved, Still open, Deferred, and the Refuted and Inconclusive findings of step 10), stage the revised changes, and return to Phase 1 with the next round number. Procedure: [Phase 3: Revise](#phase-3-revise).

12. **Conclude.** Apply standing rule B to decide whether the loop stops; [Phase 4: Conclude](#phase-4-conclude) holds the procedure.

## When to plan-review first

**Any complex task benefits from a plan review BEFORE execution**, because plan-first catches architectural holes while they are still cheap to fix, wherever the shape of the work precedes and constrains the execution: system design, refactors, paper outlines, proposal structure, migration plans, and multi-stage debugging.

**Plan-review is a Phase 0 before the staged-change loop below.** If the user asks for a plan review, or if the task clearly meets the signals below, do not apply the staged-change and drift checks under Prerequisites yet. Tell the reviewer to read the plan file directly (or paste the plan contents via the terminal path when the reviewer cannot access the file) and critique the design, not `git diff --cached`. The process is in [references/plan-review.md](references/plan-review.md). After the plan has no High findings and no new design blockers, execute the work and resume the normal staged-output review flow at Prerequisites / Phase 1.

### When to plan-first

Signals that the round-trip pays off:

- **Blast radius is large** -- multiple files, cross-cutting concerns, shared state, multiple stakeholders, or the organizing structure of a deliverable.
- **Irreversible once executed** -- publishes, submissions, deployments, immutable packages, paper submissions, external commitments.
- **History shows a pattern** -- "got the structure wrong, redo next cycle" has happened on this track before.
- **Uncertainty in the approach** -- the user is weighing alternatives and wants the design validated, not the execution reviewed.
- **Context is unfamiliar** -- new codebase, domain, audience, agency, collaborator workflow, or external constraint set, where a wrong assumption can shape the rest of the work.

### When to skip plan-first

- Change is small, local, reversible.
- The design is already worked out and only execution feedback is wanted.
- Plan and execution would be the same artifact (three-line bug fix, one-sentence footnote).

## Prerequisites

Begin each run by showing the cross-agent usage snapshot, so the quota situation is visible at this run. In Bash, run `"$HOME/.claude/hooks/_python" "$HOME/.claude/agent-quota.py"`, or run the repo copy with the project's Python (`scripts/agent-quota.py`, or `.agent-config/repo/scripts/agent-quota.py` in a consumer). Show its Claude, Codex, Agy Gemini, and Agy Claude/GPT rows. Read all percentages as **remaining** quota (headroom left), not consumed: a high value such as `93% left` is not a reason to downgrade the channel or stop the review; only a figure near `0% left` signals real quota pressure. If neither the script nor a Python runner is available, skip silently and never block the review on it.

At skill start, check for staged changes (`git diff --cached`). If nothing is staged but unstaged or untracked changes exist, list them and ask the user whether to stage all (`git add -A`), stage specific files, or abort. Do not auto-stage without confirmation; untracked files may be sensitive or unrelated. With no changes at all there is nothing to review; inform the user and stop.

Then check the other direction: a path that is staged **and** changed again since staging. Intersect `git diff --cached --name-only --no-renames` with what `git diff --name-only` and `git ls-files --others --exclude-standard` report together. A non-empty result means the reviewer would receive that path as it stood at `git add`, so its findings would read as findings about the current file. List those paths and resolve them before dispatching. Paths changed but never staged are ordinary and not this case.

The untracked list catches a staged deletion whose file came back, and `--no-renames` a path recreated after a staged `git mv`. `dispatch-gemini` refuses the drifted case itself, because its reviewer is handed an export of the index and cannot see the drift. `IMPLEMENT_REVIEW_ALLOW_STAGED_DRIFT=1` overrides that refusal for a deliberate review of the index as it stands. The other dispatchers do not enforce it yet, so this check is the only cover there. See anywhere-agents#57.

Do not stage, commit, or move `Review-*.md` files unless the user explicitly asks. Before the first review round, check whether `Review-*.md` is excluded from git, in `.gitignore` and `.git/info/exclude`. If the pattern is not excluded anywhere, append `Review-*.md` to `.git/info/exclude` so that `git add -A` during the revision flow does not accidentally stage scratch files. A committed `.gitignore` entry for `Review-*.md` satisfies this without a local edit.

## Pre-Review Checks (optional)

Before sending staged changes for review, run automated checks that catch mechanical issues locally. This lets reviewers focus on content and judgment calls instead of issues a script could find. Skip this phase if the user says to proceed directly, or if the project has no relevant tooling.

| Content type | Checks |
|---|---|
| LaTeX paper or proposal | Compile. Scan the log for overfull/underfull box warnings and undefined references. Report counts. |
| Anonymized submission | Grep staged files for author names, GitHub/lab URLs, institutional names, and tool names. Source these from the project's de-anonymization checklist if one exists; otherwise use the git user name, institution domain, and any names in the paper's author metadata or `\author{}` block. |
| Code | Run the project linter and type checker if configured. |
| Prose (`.md` / `.rst` / `.txt` / `.tex`, or prose-heavy diff) | Run `<python> <scripts-dir>/style-audit.py --repo <repo>`, resolving `<scripts-dir>` through the same lookup order as the other scripts. It finds the staged prose itself, reports `file:line:col RULE detail` for each deterministic rule, and names the rules it covers only in part or not at all, so a partial audit does not read as a clean pass. Audit the unreached rules by reading the rule pack (RULE-07 antithesis is one). Read each finding in context and fix the ones that read badly; a departure that reads well can stay. |

Report any findings to the user before Phase 1. Findings here do not go to the reviewer; fix the ones that read badly locally first.

**The style audit runs on content, and never gates the round.** Run `style-audit.py` whenever the staged diff carries prose, so skipping it is a decision someone made rather than a default. The script always exits 0, including when it finds violations and when `agent_style` is absent, so no step in the loop can fail on it. Style findings stay out of the reviewer's prompt, out of the Round history `Still open` list, and out of the verdict.

## Codex Channels

Two paths to Codex are supported. Default is Terminal-relay (manual copy-paste). Auto-terminal (`codex exec` subprocess) is opt-in via the trigger rules in Path selection below. Phase 1c dispatches it; the Codex mechanics are in [references/codex-backend.md](references/codex-backend.md), read under its Reference Index condition.

### Terminal path (default)

The user has a Codex interactive terminal window open alongside Claude Code. Claude Code prepares a copy-pasteable review prompt (summary, diff, lens, round number) and presents it as a fenced text block. The user copies it into the Codex terminal, then relays the feedback back to Claude Code.

### Path selection

1. **Default**: Terminal-relay (manual copy-paste) on every platform. Users who do not opt into another channel get the current Terminal-relay flow without modification.
   - **User-scoped default override**: when the environment variable `IMPLEMENT_REVIEW_DEFAULT_CHANNEL` is set (case-insensitive) to `auto`, `cli`, or `auto-terminal`, the synonyms the slash args accept, Auto-terminal becomes that user's default and no per-invocation opt-in token is needed, including beside a reviewer token such as `agy` or `grok`. Read the variable once at Phase 1c entry. Claude Code reads it from the `env` block of `~/.claude/settings.json`, and Codex from `[shell_environment_policy] set` in `~/.codex/config.toml`. Agy has no such setting and sees only the environment it was started in.
   - When the variable is unset, empty, or holds an unrecognized value, the shipped Terminal-relay default applies, so a typo degrades to today's behavior. Unset and empty also leave the channel line unchanged. An unrecognized value adds one clause to the channel line naming the ignored value and saying the shipped default applied, so the user does not go on believing Auto-terminal is their default.
   - **User-scoped reviewer default**: `IMPLEMENT_REVIEW_DEFAULT_REVIEWER`, read and set the same way, supplies the reviewer tokens when the invocation names none: `both`, `all`, or any of `codex`, `claude`, `agy`, and `grok`, space-separated and case-insensitive. The item 2 rules then apply as if it had been typed, so `both` resolves against the coordinator. A reviewer token in the invocation wins. Unset, empty, or unrecognized keeps Codex, and an unrecognized value adds a clause to the channel line.
2. **Auto-terminal opt-in triggers**, evaluated in detection order at Phase 1c entry:
   - Mid-flow override toward manual: "back to manual" / "next round manual" / "use terminal-relay" in the user's most recent message forces Terminal-relay.
   - Mid-flow opt-in toward auto: "next round use cli" / "next round auto codex" forces Auto-terminal.
   - Slash-arg opt-in: `/implement-review cli`, `/implement-review auto`, and `/implement-review auto-terminal` are equivalent synonyms; `auto` is the most natural keyword and is accepted.
     When `.claude/commands/implement-review.md` forwards slash arguments through `Command arguments from the slash invocation: $ARGUMENTS`, evaluate that forwarded argument string the same way as the original slash invocation.
     Manual override tokens still win before Auto-terminal opt-in tokens.
   - Plain-phrase opt-in in the invoking message: case-insensitive substring match on any of `cli mode`, `use cli`, `auto codex`, `use codex exec`, AND no negation word (`do not`, `don't`, `no`, `not`, `avoid`, `manual`) within 4 words before the matched phrase.

## Phase 1: Prepare and Send Review

### 1a. Detect content type

Inspect the file extensions in the staged diff to classify the change:

| Extensions | Content type |
|---|---|
| `.py`, `.js`, `.ts`, `.go`, `.rs`, `.java`, `.c`, `.cpp`, `.h`, `.sh`, `.yaml`, `.json`, `.toml` | `code` |
| `.tex`, `.bib` (in a paper or manuscript directory) | `paper` |
| `.tex`, `.bib` (in a proposal or grant directory) | `proposal` |
| `.md`, `.rst`, `.txt` (in a proposal or grant directory) | `proposal` |
| Everything else or mixed | `general` |

If the diff spans multiple types, pick the dominant one. The user can override by saying, e.g., "review this as a proposal." For proposals, also ask which agency lens to apply (NSF or NIH) since they use different evaluation frameworks.

### 1b. Build the review context

Prepare a review request with:

1. **Summary** -- one to three sentences on what changed and why.
2. **Diff scope** -- choose the exact diff command before assembling the prompt, and list the changed files. If every staged path is in scope, use `git diff --cached`. If staging is broader than the review scope, use `git diff --cached -- <in-scope paths>` and list the staged paths that are explicitly out of scope, so the reviewer is not left inferring the boundary. The Claude Auto-terminal backend embeds a bare `git diff --cached` in its relay prompt and has no scope argument, so use that backend only when every staged path is in scope. Do not paste the diff inline in the primary prompt, which keeps it compact across rounds. The one exception is the Auto-terminal embedded-diff retry, which embeds this same in-scope diff (decision: round checklist, step 7; procedure: [references/codex-backend.md](references/codex-backend.md)).
3. **Splitting the round** -- use a single pass by default. Split only when no shared contract crosses the boundary; keep mirrored platform files, a script and its tests, and a source and its generated or vendored copies inside one reviewer's scope. Independence is a judgement made before the split, so verify it afterwards rather than assuming it held: re-read the boundary you drew, and run the mechanical checks that apply, such as `scripts/check-parity.sh`. See anywhere-agents#41.
4. **Review lens** -- the content-type-specific criteria from [references/review-lenses.md](references/review-lenses.md). If a focused sub-lens or agency-specific lens fits better than the full lens, use it (e.g., `paper/formatting` for a layout-only change, `proposal/nsf` when the agency is known). See the lens tables in that file.
5. **Additional focus** -- specific concerns beyond the generic lens, often the highest-value part of the prompt because it catches real bugs that generic criteria miss. **Always ask the user explicitly rather than guessing.** Recurring project concerns belong here (for example anonymization checks, page-limit compliance, or terminology drift). If there are none this round, write "none" rather than padding the line. When a focus names the writing rules, paste the banned-word list from `AGENTS.md` § Writing Defaults and the four checks (a sentence whose point arrives late, repeated sentence openers, casual dashes, contractions) into the focus item itself, using the wording of the General lens item 7 in [references/review-lenses.md](references/review-lenses.md); never send the reviewer to `AGENTS.md` for them.
6. **Round number** -- which iteration this is (starting at 1).
7. **Variant targets (multi-target reviews)** -- if the staged files cover two or more variant targets that should be reviewed separately (long + short paper version, narrative + appendix tracker, internal + external report, primary + supplement), list each target by directory or file pattern. Tell the reviewer to review each target in its own top-level section and then add a cross-variant drift check at the end (tables that should match, claims that should be consistent, terminology that should align).
8. **Round history** (rounds 2+ only) -- a one-line-per-finding summary of what prior rounds raised and how each was resolved. Tag each finding as `Resolved`, `Still open`, `Deferred`, `Refuted`, or `Inconclusive`. The last two come from the Phase 2.5 verification step (see below); they let the reviewer see when a prior factual claim did not hold up under verification, with a pointer to the evidence so the reviewer can either retract or sharpen the claim. Example:
   ```
   Prior findings:
   - DMP listed wrong project name (Resolved — fixed in round 1)
   - Budget table exceeds page width (Still open)
   - Consider reordering Section 3 (Deferred — user decision)
   - Citation [Smith2023] does not exist (Refuted in round 2 — arxiv.org/abs/2023.XXXXX confirms paper)
   - Compile error in section 4 (Inconclusive in round 2 — could not run latexmk in this env)
   ```

### 1d. Auto-watch (Terminal-relay and Auto-terminal channels)

After Phase 1c emits the Terminal-relay prompt or dispatches Auto-terminal (and records the expected reviewer set + emission/dispatch time), the skill **automatically** launches one background watcher per expected reviewer. Each watcher detects when its reviewer writes its `Review-<Name>.md`, eliminating the manual "done" relay. The watcher runs by default for both channels; the user does not need to confirm. To opt out, the user can say so explicitly (e.g., "stop auto-watch", "manual mode this round") and the skill terminates the background process and falls through to the wait-for-user path.

Launch the platform-appropriate watcher script immediately after emitting the prompt, using positional arguments `(FILE_GLOB, ROUND_NUMBER, EXPECTED_REVIEWERS)`. Look up `auto-watch.{sh,ps1}` through the same three roots as the Auto-terminal scripts. `FILE_GLOB` is the reviewer's exact `Review-<Name>.md` and `EXPECTED_REVIEWERS` its normalized name (e.g., `Codex`). A multi-reviewer round launches one watcher per reviewer, each with its own state directory, never one watcher over `Review-*.md`. Run the watcher in the background so the skill can keep accepting user input while it polls. On the Auto-terminal path, set `IMPLEMENT_REVIEW_STATE_DIR` to the absolute path from the dispatcher's `STATE-DIR` line when launching the watcher. That hands the directory over instead of leaving the watcher to find it.

When the watcher emits `DONE <path>`, resume Phase 2 immediately for a single-reviewer round. In a multi-reviewer round, that reviewer is ready for intake; begin consolidation only after every reviewer has a ready report or a confirmed failure. The watcher's path output is informational; Phase 2 still re-lists `Review-*.md` itself and applies the freshness + scope partition described below. A reviewer whose watcher ends without a report is handled by Phase 2's missing-reviewer steps once every other reviewer is resolved.

When the watcher emits `AUTO-REDISPATCH ...`, the bounded retry has started; keep watching the same logical dispatch and state directory. No user action is required.

When the watcher emits `STALL <state-dir>`, surface the silence warning and inspect or continue monitoring the dispatch (round checklist, step 6).

When the watcher emits `TIMEOUT`, print `Auto-watch timed out after 60 min; reply 'done' when the reviewer finishes.` and wait for the user; an opt-out, a user interrupt, or a failed watcher launch fall through to the same wait-for-user path, and no Phase 2 logic depends on whether auto-watch ran. A watcher `REAP-UNKNOWN` is resolved in the foreground as round checklist, step 6, says. Recovery after `TIMEOUT` and the watcher's `STREAM-DEAD` line are in [references/failover-and-recovery.md](references/failover-and-recovery.md).

**When the harness reports the dispatch or the watcher as stopped** (a background-task notification carrying `killed`, whose summary reads `Background command "..." was stopped`): handled by round checklist, step 6. `await-review` replaces the watcher for the rest of that round.

**What counts as a death** is set by round checklist, step 6. A reviewer can publish twice in one round and the second write is the one worth having, so a review under the wrong round marker is no evidence that the round ended.

## Phase 2: Intake Feedback

### Phase 2.0: Health check (Auto-terminal only)

The Auto-terminal channel runs 10 structural health checks and 3 Substance heuristics on each reviewer's review file; Terminal-relay skips them. Run them once per reviewer, with that reviewer's state directory (from its dispatcher's `STATE-DIR <abs-path>` line) and exact review file, using the command in round checklist, step 7. [references/health-check.md](references/health-check.md) holds the check table, the Substance heuristics, and false-positive tuning; open it when `health-check` prints any `FAIL`, or a `WARN` marker you do not recognize.

**Outcomes**: round checklist, step 7, decides each outcome (advance with no inspection, inspect a `WARN`, or refuse on a `FAIL` while the other slots stay active), and step 8 lists the conditions for advancing with no inspection.

**Required dispatch state contract**: Missing or stale `<state-dir>/pre-mtime` or `<state-dir>/timestamp` is `FAIL`, because Health check 2 and the time-floor heuristic cannot be trusted without them. A missing `<state-dir>/tail` and a missing review file are covered in round checklist, step 7.

**Exit codes**: `health-check` exit codes are in round checklist, step 7. `stall-watch` exits 0 whatever it detected, and a `REVIEW-READY` from `await-review.py` says nothing about Checks 4 to 10, which that review can still fail.

#### Phase 1d coordination (Auto-terminal-specific silent-intake rule)

For Terminal-relay, auto-watch `DONE` is sufficient signal to advance that reviewer into intake. For Auto-terminal, check the eight conditions of round checklist, step 8, for each reviewer on its own evidence (its `DONE` line, dispatcher exit, health-check output, and state directory). `STREAM-DEAD` is an Auto-terminal runtime failure handled by Phase 1c failover ([references/failover-and-recovery.md](references/failover-and-recovery.md)).

### Phase 2.1: Partition and classify (all channels)

When every expected reviewer has a ready report or a confirmed failure, or the user says the reviewers are done, list the files matching `Review-*.md` at the repo root and partition them along two axes before trusting any of them; round checklist, step 8, says which to read, what to report, and when to ask.

**Freshness axis**: **current-round** (first line is `<!-- Round N -->` with N the current round number), **stale-round** (a different round marker), **empty**, or **unreadable** (cannot be read, or has a malformed or missing round marker).

**Scope axis** (if the expected reviewer set from Phase 1c is known): **expected** (the reviewer name extracted from the filename is in the expected set) or **unexpected** (the name is not in the set, possibly a leftover artifact from an earlier task that happens to share the round number).

A current-round unexpected file may be a leftover from another task or a reviewer the user invoked without announcing. A corroborating signal is, for example, that its scope matches the current staged files or that the reviewer was named in the conversation; an mtime clearly older than the Phase 1c emission time weakly suggests a prior-task artifact.

For an expected reviewer that is missing from the current-round, expected bucket (absent, or its file stale, empty, unreadable, or unexpected) and whose dispatch is neither active nor confirmed failed, build the follow-up prompt from the save contract that opens the Terminal path template in Phase 1c, with the current round number, and name the reviewer so the user knows where to paste it.

Classify and categorize the findings by round checklist, step 9, labelling a Single-source finding with its file (for example "from Review-Codex.md"). A typical Will fix is a main-path bug, a wrong fact or unsupported claim, a step a reader cannot follow, or a risk to user data; a typical Decline is a corner case that needs two failures at once, a hand-edited internal file, or an unusual environment. Verify factual claims first (round checklist, step 10); a Refuted finding is not applied whatever its category. For follow-up questions within the same review round, prepare a short prompt the user can paste into the reviewer.

## Phase 2.5: Verify Factual Claims (when triggered)

After Phase 2 categorization and before applying the categorized list, verify the findings the trigger below selects (round checklist, step 10), so a wrong finding is not applied and a refutation leaves an evidence trail. [references/health-check.md](references/health-check.md) lists a method per claim type, with an example; open it when a claim needs one.

### Trigger

Round checklist, step 10, states when verification fires and when it is skipped. A checkable claim is, for example, citation existence, code behavior, link reachability, a page-limit or word-count assertion, a compile or type error, or an anonymization leak. Stylistic, opinion-based, and structural findings (term choice, paragraph order, tone, organization) have no factual ground truth to verify against. The embedded-diff retry procedure is in [references/codex-backend.md](references/codex-backend.md).

**Why Medium-from-retry-channel is mandatory-verify**: the retry sees only the diff hunks, so a claim of the form "X is missing" can be wrong when X sits in a non-diff line. One dogfooding case: a Medium claim that a regex set was case-sensitive was Refuted because the scanner applied `re.IGNORECASE` at compile time in a non-diff line.

### Outcome

Record Verified, Refuted, or Inconclusive for each verified claim and act on it as round checklist, step 10, says. Refuted also covers an issue that does not reproduce, and Inconclusive a verification that could not run (no internet, no test runner, a claim under-specified) or returned ambiguous results.

### Round history integration

Findings flagged Refuted or Inconclusive enter the next round's `Prior findings` block (see Phase 1b item 8) so the reviewer sees the evidence and can either retract the claim or sharpen it. Refuted findings appear as `(Refuted in round N — <one-line evidence>)`. Inconclusive findings appear as `(Inconclusive in round N — <reason>)`, prompting the reviewer to supply a more specific or pre-verified check.

## Phase 3: Revise

Apply the fixes, update the round history, stage, and start the next round as round checklist, step 11, says. This history carries forward into the next round's prompt (Phase 1b, item 8).

## Phase 4: Conclude

Stop when rule B of the round checklist says to, and present the summary it names.

## When Not To Use

- Trivial changes where review adds no value (typo fixes, config tweaks).
- Changes that require running tests or builds to validate -- run those first, then review.
- When the user wants a single-shot review with no revision loop; just ask a reviewer directly.
